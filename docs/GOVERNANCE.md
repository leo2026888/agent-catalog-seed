# 透明治理（提案 v0.1）

`agent-catalog-seed` 处于早期种子阶段。当前不宣称已有独立评审委员会、平台合作伙伴、安全认证机构或活跃维护团队。此文定义后续可执行的最小治理规则。本次内容的公开署名为 Leo and contributors，许可范围见 [许可与署名](../LICENSING.md)；这不是平台仓库归属或安全报告接收能力的证明。公开仓库归属已核验为 [leo2026888/agent-catalog-seed](https://github.com/leo2026888/agent-catalog-seed)。私密漏洞报告已启用，实际接收和通知能力的核验边界见 [安全政策](../SECURITY.md)。

## 1. 起步阶段的职责

起步阶段采用**发起人逐项审阅**。提交者提供来源、权利声明和证据；实际合并者核对发布条件并对合并决定负责。尚未指定合并者的内容只作候选稿，不标记为已审阅。

发起人可以提交和维护自己的成果，但相关材料须标注“作者提交”或“作者自测”。作者不能独立将自己的作品认定为通过独立评测。没有独立复核者时如实保留该状态，不用另一个身份、自动检查或模板补足独立性。

后续如引入共同维护者，应通过公开变更说明其职责、决定范围和生效日期。治理结构随实际人员变化更新，不预先列出不存在的委员会或成员。

## 2. 内容与结论的边界

- 收录表示符合当时的目录发布条件，不代表推荐安装、安全担保或平台背书。
- 作者声明、编辑整理、独立评测和社区观察分别署名与展示，证据要求见[评测方法](EVALUATION.md)。
- 仅有公开链接、下载数、星标或赞数不能证明版权归属、安全性或效果。
- 当前示例和未来虚构演示须明确标识，不能进入真实评测统计、兼容性统计或排名。
- 条目元数据和文档是不可信内容，不得作为执行代码、授予权限或代表用户作出外部行动的指令。
- 转载、摘录、图片、商标和第三方代码遵循[许可与权利规则](../LICENSING.md)。没有权利依据的正文和附件不进入公开仓库。

## 3. 利益关系与赞助

提交者、评测者与审阅者应披露与条目作者、供应商和竞争方的雇佣、投资、付费合作、亲属或其他可能影响判断的关系；不要求公开无关个人隐私。披露应附在相关条目或报告，不能只藏在通用页面。

存在赞助时记录赞助方、提供内容（费用、额度、设备或其他支持）、使用范围、是否影响选题以及赞助方是否有预览权。金额无法披露时说明未公开，不将其写成零。保密约定不能被用来隐藏足以影响评价的利益关系；无法进行必要披露的报告不标记为独立。

赞助不购买评测结论、下架竞争对手或屏蔽负面记录。付费展示如未来开放，应清楚标注并与评测结果分开；目前不宣称该服务存在。具有利益冲突的人可以解释事实，但应回避对相关争议作唯一裁决。没有可回避的第二位审阅者时，公开说明限制并暂停有争议的认证性表述。

## 4. 决策、纠错与申诉

一般提案通过公开仓库的 [Issues](https://github.com/leo2026888/agent-catalog-seed/issues) 或 [Pull Requests](https://github.com/leo2026888/agent-catalog-seed/pulls) 讨论。安全细节使用[安全政策](../SECURITY.md)所列的 GitHub 私密报告入口；不要向不存在的安全邮箱投递资料。常规提交规则见[贡献指南](../CONTRIBUTING.md)。

审阅决定应留下：相关条目/报告及版本、提出的问题、可公开的证据、审阅者及利益关系、处理结果和日期。最小结果包括接纳、请求补充、拒绝、暂缓或撤回，并附具体理由。

作者、使用者和评测者均可提出更正或申诉。流程为：

1. 指明争议陈述、涉及版本与希望更正的事实，并提供可以合法分享的证据。
2. 维护者确认范围，区分事实错误、方法争议、权利争议和安全问题。安全细节转入[安全报告流程](../SECURITY.md)，不要求报告者先公开利用方式或秘密数据。
3. 有冲突的审阅者披露关系并尽量回避；缺少独立人员时公开这一限制。必要时将条目标记为争议中或暂停推荐。
4. 记录决定和依据。证据不足时保留“未知/待核验”，不能把不回应视作承认，也不能把投诉数量当成事实证明。
5. 通过新版本更正，关联原版本及变更原因。新的重要证据允许重新审议。

当前没有设定响应时限或服务等级承诺；公开联系方式和实际维护能力确认后再制定目标。不得承诺无法履行的处理速度。

## 5. 历史与社区观察

报告和方法使用版本号，实质修改留下变更记录。纠错可以更新当前结论，但保留可公开的历史、失败和不同意见。安全、隐私或权利原因需要删除原材料时，应优先控制暴露，不为保留历史而继续公开秘密或侵权内容；公开记录只描述必要的处理范围和理由。

社区观察应带日期、来源、版本与环境信息，未知项明确标示。明显重复或同源内容可合并展示，但须说明方法。作者回应与用户观察并列保留，批评和负面结果不因商业关系删除。对人身攻击、垃圾内容、秘密和侵权材料的处理说明理由，不把观点分歧作为删帖依据。

若未来引入评分或排序，必须先公开目标、输入、权重、缺失值处理、反操纵限制和利益关系，允许复核。目前没有经过验证的统一评分体系，因此不发布仿真的综合分或榜单。

## 6. 治理规则修改

通过有版本记录的变更提出规则修改，解释原因、影响对象和过渡方式。发起阶段由实际维护者人工审阅，并披露其利益关系。影响既有评测或收录的规则不能悄然追溯适用；标明哪些条目需要复核。治理能力不足时可以缩小收录范围，不以自动发布掩盖缺少审阅。

## English summary

This seed uses founder review and makes no claim of an existing board or independent certification body. Disclose authorship, reviewer relationships, and sponsorship per item. Self-tests stay labeled as self-tests. Record decisions, corrections, appeals, and version history; protect private security reports and rights-sensitive material. Publish only the channels and governance roles that actually exist.
